# 作業手順・運用ガイド

最終更新日：2026-11-05（3限月の完全性検証を追加）

## 1. 通常時のデータ更新

### 自動更新

1. GitHubリポジトリのActionsを開く。
2. `Update JPX Option Data` の実行履歴を確認する。
3. 5分間隔のスケジュールで実行される設定だが、GitHub Actionsの起動時刻は保証されない。
4. 実行が完了したら、`data/latest.csv` の更新時刻・限月・レコード件数を確認する。
5. GitHub Pagesを再読み込みし、表示がCSVと一致することを確認する。

### 手動更新

1. [Actions](https://github.com/uro-o/jpx-option-data-realtime-html/actions/workflows/update-option-data.yml)を開く。
2. `Update JPX Option Data` を選択する。
3. `Run workflow` を実行する。
4. 実行ログの `DYNAMIC QRI CONTRACTS` で3限月とQRI URLの対応を確認する。
5. `GET JPX OPTION DATA` のログで各限月の取得件数・QRI更新時刻・取引日を確認する。
6. 最後まで成功したことを確認する。
7. `data/latest.csv` の内容を確認する。

注意：手動実行は取得処理を開始するだけです。データが完全であることやDiscord通知が成功したことを自動的に保証しません。

## 2. データの正常性チェック

最新CSVを確認するときは、最低限次の項目を確認します。

- [ ] 期待する3限月が存在する
- [ ] Actionsログに `[VALIDATION] All 3 contracts contain complete CALL/PUT strike pairs.` が出ている
- [ ] 検証エラーが出ていない
- [ ] 3限月の限月キーが重複していない
- [ ] 各限月にCALLとPUTが両方ある
- [ ] CALLとPUTのStrike範囲・件数に不自然な偏りがない
- [ ] QRI更新時刻が取得対象ページと一致している
- [ ] `collected_at` が今回の実行時刻に更新されている
- [ ] `trading_day` と `last_trading_day` が不自然でない
- [ ] OI・出来高・価格・IVの空欄率が普段と比べて急増していない
- [ ] 空欄が画面上で「—」と表示され、数値0として集計されていない
- [ ] OIに欠損がある限月でMax Painが計算・更新されていない
- [ ] 同じ限月・種類・Strikeの重複行がない
- [ ] HTML表示とCSVの数値が一致する

3限月の取得成功、各限月のStrikeごとのCALL/PUTペア、重複レコード、想定外の限月はPython側で自動検証します。検証に失敗した場合は処理をエラー終了し、`latest.csv`・`differences.csv`・日次履歴の更新へ進みません。正常終了時も、ログとCSVの件数・Strike範囲を確認してください。

## 3. 取引日と取得時刻の見方

CSVには次の時刻・日付があります。

- `qri_update_time`：QRIページに表示された更新時刻
- `collected_at`：このプログラムが取得した時刻（JSTのISO形式）
- `trading_day`：QRIが示す取引日
- `last_trading_day`：限月の最終取引日としてページから取得した日付
- 履歴ファイル名の日付：QRIの取引日を基準にした日付

夜間取引では、JSTの暦日とQRIの取引日が異なることがあります。履歴分析では `collected_at` と `trading_day` の両方を確認してください。

## 4. 履歴保存のルール

`run_option_data.py` は、JST 15:45以降に最初に成功した実行で履歴を保存します。

保存先：
`data/history/<限月>/<取引日>.csv`

保存済みマーカー：
`data/history/.fixed-1545-<取引日>.done`

マーカーが存在すると、その取引日の固定時刻スナップショットは保存済みと判断し、後続実行で同じ日の履歴を上書きしません。

### 注意事項

- 15:45ちょうどのスナップショットではなく、15:45以降の最初に成功した実行のスナップショットです。
- 取得が遅れれば、保存時刻も遅くなります。
- 現行コードは、取得できた限月をグループ化して保存する構造です。3限月すべてが揃っているかの検証を追加する必要があります。
- マーカーは取引日単位で作られます。限月別の保存がすべて完了した後に作成される設計ですが、データ品質チェックは別途必要です。
- 過去履歴を手動で修正する場合は、対象CSVとマーカーの関係を確認し、意図せず再保存・上書きしないようにしてください。

## 5. Discord通知の確認

現行の `get_option_data.py` は環境変数 `DISCORD_WEBHOOK_URL` を読み込みます。

確認事項：
1. GitHub側でWebhook URLを安全に保存しているか。
2. workflowから環境変数として渡しているか。
3. 実行ログに通知送信成功／失敗が出ているか。
4. Discord側にメッセージが届いているか。

**現状の注意：** workflowのYAMLには `DISCORD_WEBHOOK_URL` をSecretsから環境変数へ渡す記述が確認できていません。また、送信失敗時に通知を永続保存して再送するキューもありません。通知が届かない場合、Webhook設定だけでなく実行フロー全体を確認してください。

Webhook URLをログ・コミット・画面共有へ出さないでください。

## 6. エラー発生時の確認順序

### A. Actionsが起動しない

1. workflowが有効か確認
2. cronのUTC/JST換算を確認
3. Actionsの実行履歴とGitHub側のスケジュール遅延を確認
4. 必要ならworkflow_dispatchで手動実行

### B. QRIデータが取得できない

1. 失敗した限月とURLをログで特定
2. QRIページがブラウザで表示できるか確認
3. HTML構造やテーブル列が変わっていないか確認
4. HTTPステータス・タイムアウト・解析件数を確認
5. 3限月の完全性検証が失敗した場合は既存CSVが保持されることを確認する
6. QRIのページ構造変更が疑われる場合は、取得件数・CALL/PUTペア・重複検証のログを確認する

### C. Strike数が急に減った／限月が欠けた

1. `run_option_data.py` の限月計算を確認
2. 3限月とQRI URLの対応を確認
3. CALL・PUT別の件数とStrike範囲を確認
4. 最新CSVと前回CSVを比較
5. HTMLの表示フィルターではなく、まずCSV自体にデータが存在するか確認

### D. Max Painが表示されない／不自然

1. 対象限月のCALL・PUT OIが取得されているか確認
2. 空欄と実際のゼロを区別する
3. OIが不完全な状態で計算されていないか確認
4. HTMLの計算対象Strikeと元CSVを照合

### E. Discord通知が来ない

1. `DISCORD_WEBHOOK_URL` の登録状態を確認
2. workflowで環境変数として渡しているか確認
3. QRI更新時刻が前回から変わったか確認
4. 差分条件・通知上限・送信ログを確認
5. 失敗通知が再送されない現行仕様に注意する

## 7. コード変更時の標準作業手順

1. **現状確認**：変更対象ファイル、呼び出し元、関連データ、Actions設定を読む。
2. **仕様確認**：目的、入力、出力、閾値、保存先、異常時の挙動を決める。
3. **影響範囲確認**：CSV列やHTML表示、通知、履歴への影響を洗い出す。
4. **変更**：一度に複数の責務を大きく変更せず、小さな単位で行う。
5. **構文検査**：Pythonのコンパイル、HTML/JavaScriptの構文を確認する。
6. **単体テスト**：`python -m unittest discover -s tests -v` を実行し、正常系・限月欠落・CALL/PUT欠落・重複・想定外限月を確認する。
7. **Actionsテスト**：手動実行し、ログ・終了コード・生成ファイルを確認する。
8. **データ検証**：限月別・CALL/PUT別の件数、Strike範囲、空欄率を確認する。
9. **画面検証**：HTML表示とCSVが一致することを確認する。
10. **文書更新**：README、データ辞書、改善課題、更新履歴を更新する。
